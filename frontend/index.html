RecoverAI detects failed payments in a simulated merchant, diagnoses why each one failed, decides on a bounded recovery action, checks that decision against a policy engine neither the strategy engine nor an LLM agent can bypass, executes it, and records the full explainable trail — end to end, autonomously. What's actually running under the hood

Deterministic risk engine
Every failure is scored risk_score = failure_probability × amount × recovery_probability, blending payment-method and customer-level historical rates — no ML needed here, and none used.
ML recovery model
Logistic regression, 5-fold cross-validated, never sees the simulator's hidden ground-truth label (no leakage). Click Train recovery model below to see it evaluated live against a rule-based baseline — including when the simple baseline wins, reported honestly either way.
Not yet trained this session
Expected-value strategy engine
7 candidate actions compared by expected value every time. STOP is always available at exactly ₹0 EV — a structural guarantee the engine can never recommend a money-losing action.
LLM agent (Groq) checking…
Tool-calling agent invoked only for genuinely ambiguous cases (close expected values, or high-value transactions) — never in the bulk automatic pipeline, by design. 4 read-only tools plus one structured decision-submission tool.
Deterministic policy engine
8 independent guardrail checks — valid action, customer opt-out, retry limit, discount limit, intervention frequency, high-value threshold, automated amount limit, agent-requested approval — combined with strict DENY > ESCALATE > ALLOW precedence. Neither the strategy engine nor the LLM agent can bypass it.
Fair experimentation
Every condition compared against the same transaction using the same random seed, so a strategy's higher success rate reflects real decision quality — not luck. Click Compare strategies below to run it.
Performance engineering
Database indexing, batched commits, and SQL-side aggregation replaced per-event commits and full-table scans — a measured 7x speedup, near-linear scaling past 20,000 transactions.
Not yet measured this session
Real Razorpay integration checking…
Genuine test-mode Payment Links API calls (not mocked), restricted to customer-facing strategies only — the simulator remains the sole source of truth for whether recovery actually succeeded.

⚠️ Chaos mode — simulate a real provider outage

Temporarily degrades ONE payment provider's real success odds, generates a "before" batch and a "during" batch through the full closed loop, and shows exactly what shifted. Chaos mode only changes ground truth (app/simulator/chaos.py) — the risk engine, strategy engine, and policy engine never see it. Everything below is emergent, computed from real observed data, the same way a real production system would have to detect a real outage.
